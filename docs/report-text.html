Introduction

GiftBox Studio lets a customer assemble a small, personal gift box, decorate individual gifts and choose a pricing offer. The application then creates an order and shows status notifications to two different audiences. Its purpose is to demonstrate six coordinated design patterns in a complete Java application with an accessible browser interface.

A gift box is a useful domain because several kinds of change occur independently: the catalogue can grow, gifts can receive optional presentation, discount policies can change, and different observers can react to order progress. Separating these responsibilities makes the relationships between the patterns visible without requiring a large business system.

What this submission contains

The project includes Java source, HTML/CSS/JavaScript assets, build scripts, automated tests, this report, editable UML sources and actual screenshots. All pricing and order rules run in Java. The browser sends selections and displays the server response; it does not replace the Java implementation with a separate pricing simulation.

Scope: a local educational demonstration. There is no payment processing, login, real delivery or outbound email. Orders remain in memory until the Java process stops.

FINALSDP / 02

Problem, scope and architecture

Functional requirements

The user selects one to twelve gifts from Book (1500 KZT), Candle (800 KZT) and Tea collection (1200 KZT). Each item can receive gift wrap for 200 KZT and a ribbon for 100 KZT. A recipient is required; a short message is optional. The application computes the decorated subtotal and applies exactly one offer to the whole box.

An order starts in CREATED, moves to PACKING and ends in READY. Each valid change notifies the customer view and the packing desk. Skipping stages, repeating a completed transition, creating an empty box and selecting unknown products are rejected.

Dependencies and runtime

The Java core needs JDK 11 or newer and no external libraries. The HTTP adapter uses the JDK HTTP server and listens on 127.0.0.1. The project can therefore be demonstrated offline after cloning or extracting it. JavaScript uses standard browser APIs, and all illustrations are local CSS shapes, so no remote assets are required.

Data and validation

Amounts are nonnegative whole KZT stored as int. Percentage calculations use a long intermediate and floor the final total. Math.addExact rejects overflow while adding gift and decoration prices. The builder trims text, limits the recipient to 60 characters and the message to 200, and copies its item list when building the result.

The box list is immutable, but this is not a deep copy of arbitrary Gift objects. Built-in products and decorators are immutable; third-party Gift implementations must keep their values stable. These assumptions are documented in CONTRACT.md.

FINALSDP / 03

Creating gifts and building a box

Factory Method

GiftCreator is the abstract creator. Its public createGift operation calls the protected createProduct factory method and checks the returned product. BookCreator, CandleCreator and TeaCreator override createProduct to supply different Gift implementations. The product classes expose only description and price and carry no decoration or discount logic.

Evidence: factory/GiftCreator.java and the three concrete creator classes. The map in GiftBoxFacade chooses a creator by a UI key; that map is not the Factory Method. The pattern is the overridable creation operation used by the superclass. A test injects a new creator without modifying the facade algorithm.

Builder

GiftBox.Builder collects the recipient, message and gifts step by step. build validates the required state and constructs a GiftBox. The product takes a copy of the builder list, so later builder reuse cannot add items to an earlier box. Pricing remains outside the builder because it is a separate responsibility.

The excerpt illustrates the sequence in GiftBoxFacade.quote; its production loop also checks selection for null. The actual builder is in builder/GiftBox.java. Tests verify empty input, text limits, the 12-gift limit, list immutability and builder reuse.

Why both patterns are useful

Factory Method controls which individual product is created. Builder controls how an aggregate is assembled. They solve different problems and both appear in one normal request: the facade asks a creator for a Gift, decorates it, and adds it to a builder. A simple constructor would be enough for a fixed two-field object, but this box has optional text, repeated items and validation at completion.

FINALSDP / 04

Temirlan’s part: decoration and pricing

Decorator

Gift is the component interface. GiftDecorator also implements Gift and stores one wrapped Gift. GiftWrap and Ribbon are concrete decorators. Both delegate to the enclosed object, then extend its description and price. They can wrap products supplied by any creator without knowing their concrete class.

A book remains 1500 KZT; the wrapped object reports 1800 KZT. This avoids a subclass for every combination such as BookWithRibbonAndWrap. Reversing these two wrappers changes description order but not the sum. Repeated wrapping is possible in the domain API, while the UI deliberately offers each option once per item.

Strategy

DiscountStrategy declares applyDiscount(subtotal). PriceCalculator is the context: it stores a strategy, supports replacement and calls the interface after calculating the decorated subtotal. NoDiscount, StudentDiscount, HolidayDiscount and ThresholdDiscount are the concrete strategies.

A percentage parameter alone would handle the first percentage policies. The threshold policy deliberately uses a different algorithm, making interchangeable behavior more meaningful. The calculator is unchanged when the policy changes. The HTTP adapter still registers the available choices; open/closed design does not mean every file is forever unchanged.

FINALSDP / 05

Orders, events and the facade

Observer

Order is the publisher and maintains a list of OrderObserver subscribers. CustomerNotifications and PackingDesk implement the callback independently. Each records its own in-app history. subscribe avoids duplicate registrations; unsubscribe removes a subscriber. The publisher iterates a snapshot of the subscriber list while dispatching an event.

The enum order defines the current linear workflow. Adding branching states would require an explicit transition policy. Events are synchronous and in memory. They are not network pushes or real email; the browser receives both updated histories after its status request.

Facade

GiftBoxFacade provides quote and placeOrder. The client supplies recipient text, gift selections and a discount strategy. The facade resolves creators, applies wrappers, feeds a builder and invokes PriceCalculator. placeOrder additionally constructs OrderReceipt, which owns an Order and attaches both observers. A quote has no order or notification side effects.

Evidence: facade/GiftBoxFacade.java, OrderReceipt.java and observer/Order.java. The facade hides the assembly sequence from the browser and HTTP routing code. It does not take over every subsystem responsibility: builder validation, arithmetic and observer dispatch stay in their own classes.

One coordinated scenario

A single order exercises Factory Method, Decorator, Builder, Strategy and Facade. Later status updates exercise Observer on that same order. All six are operational within one application, although not every pattern executes at the same instant. This matches the assignment’s coordination requirement.

FINALSDP / 06

Principles and Clean Code decisions

Defensive behavior

Invalid domain input is rejected near its owner. The HTTP layer limits request bodies, rejects unsupported methods and origins, and serves only an explicit list of local assets. The UI uses textContent for user text instead of injecting HTML, clears stale quote values while recalculating, and ignores older responses after a selection change.

Trade-offs, not perfection

The tiny output-only JSON encoder keeps the project dependency-free; it is not a general JSON parser. The HTTP server is intentionally sequential and local. Observer exceptions are not isolated: built-in callbacks are simple list appends, but a future unreliable subscriber needs error handling. These choices keep the defense manageable while making the extension points visible.

How to read the relationships

GiftDecorator is both a Gift and a holder of another Gift. This is the central structural relationship of Decorator. PriceCalculator holds a DiscountStrategy; concrete policies satisfy the same operation. Replacing that reference changes behavior without changing the gifts or the summation algorithm.

Verification and reproducibility

Important test cases

The user-part suite covers wrapper composition, unchanged base objects, independent Gift implementations, runtime strategy replacement, once-per-box discounting, rounding, empty lists, nulls, negative amounts, invalid strategy output and overflow. The project suite covers creator extensibility, builder snapshots, text/item limits, threshold boundaries, unsubscribe, invalid state changes and full six-pattern integration.

HTTP checks exercise the real server: valid quotes, JSON escaping, created orders, both notification streams, invalid transitions, unknown gifts and offers, empty input, excessive item count, missing orders, method restrictions, oversized bodies and cross-origin rejection. These checks do not establish production security or multi-user scalability.

Run from the source archive

Verification environment: Windows, JDK 25 compiling with --release 11, Chrome. JDK 11 itself and Linux/macOS launch scripts were not executed in this environment. Python is required only for the optional HTTP tests, not for running the application.

FINALSDP / 12

Conclusion and further work

Conclusion

GiftBox Studio demonstrates six distinct patterns in one working application. Factory Method creates products; Decorator enriches individual gifts; Builder produces a box; Strategy calculates the selected offer; Facade connects the use case; Observer reacts to order progress. The browser interface makes their combined effect visible, while Java tests make important boundary behavior reproducible.

The strongest part of the design is the separation of gift structure, pricing and order events. The threshold offer demonstrates a behavior change that is more than a different percentage. The project remains intentionally small enough to trace a browser action to a specific method during the defense.
